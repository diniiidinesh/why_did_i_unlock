## 1. What this app is

Why Did I Unlock (working name) is an Android-first digital-wellbeing app. Core loop:

1. **Intent capture** — on phone unlock, a prompt asks "What are you unlocking for?" (presets / voice / custom text).
2. **Floating bubble** — the declared intent persists as a draggable overlay bubble across all apps until the user completes it.
3. **Optional timer** — a countdown can be attached; the bubble changes color / pulses as time runs out.

The defensible combination is **bubble + timer**, NOT the unlock prompt on its own (see §10). Positioning is deliberately drifting from "unlock interceptor" toward "phone session manager."

## 3. Sprint 3 — local storage + prompt triage + history (shipped, merged to `main` 2026-07-22, PR #7)

Full design/rationale/test plan lives in the plan file this was built from (not git-tracked); this section is the durable as-built record. `flutter analyze` clean, `flutter test` green (27 tests); on-device manual verification complete (`docs/TEST_PLAN.md` 16–29).

**As-built, differs from the original plan in two ways — both were deliberate scope decisions made mid-build, not drift:**
1. **Two-column schema, not one.** `intent_log` has `kind` (`'intent'` | `'no_intent'`) as a separate column from `source` (`'preset'` | `'custom'` | `null`) — outcome vs. input-method are different questions and this keeps "purposeless-unlock rate" (`WHERE kind='no_intent'`) queryable without polluting the source buckets. `client_id` (TEXT UNIQUE) makes writes idempotent (`INSERT OR IGNORE`). "Just Like That" ("no real reason") unlocks ARE logged (`kind='no_intent'`, `completed_at=declared_at`) — this was originally out of scope, added because the purposeless-unlock rate is the core behavioral metric the app is trying to surface.
2. **Triage is cooldown + probability, not cooldown alone.** A deterministic 1-minute cooldown floor (never re-prompt within the configured cooldown of the last event — kills back-to-back nagging) ANDed with a probability gate above it. **Default since 2026-07-25: probability 100% + 1-min cooldown** — the Sprint 3 50% default read as "broken / random skips" in friend testing more often than it helped resist habituation (Vance & Anderson, fMRI, MISQ 2018); probability remains tunable in Settings for users who want unpredictability. Both were hardcoded named constants (`lib/main.dart`) at Sprint 3 time — **Settings shipped in Sprint 4 as `lib/settings_screen.dart` (T13), via `AppSettings`** — an instance-based strategy plugs in as a new policy, no call-site rework. Onboarding + Settings copy explain the defaults so users aren't surprised.
3. **A minimal read-only history screen** (`lib/history_screen.dart`, opened from `HomeScreen`) was added to scope — lists recent events, styles `no_intent` rows distinctly. No edit/delete.

**Where things live:** `lib/intent_store.dart` (the `IntentStore` repository — `open()`/`insertEvent()`/`lastCompletedAt()`/`recentEvents()`, all parameterized queries, WAL journal mode), `lib/prompt_policy.dart` (the triage policies above), `lib/history_screen.dart`. Full engine/write-path architecture is in `docs/ARCHITECTURE.md` §1/§3/§5 — read that before touching any of this, especially the overlay↔background relay.

**Four real bugs found and fixed while building this — all are durable gotchas, see `docs/ARCHITECTURE.md` §5 for the full detail:**
- **`FlutterOverlayWindow.shareData()` must be fire-and-forget (`unawaited(...)`), never `await`ed, from the overlay isolate.** The plugin's native overlay-side handler forwards the message but never replies, so an awaited call hangs forever — this silently broke the bubble's × button outright (the dismiss handler never reached `closeOverlay()`) until fixed. Any future code that calls `shareData()` from the overlay isolate must NOT await it. (This transport was later replaced entirely by `IsolateNameServer` ports — see the next bug — but the fire-and-forget lesson carries over to any native-bridged call.)
- **`shareData()`/`overlayListener` routes through a single static native field (`WindowSetup.messenger`)**, set by whichever engine attached the plugin last. Our app registers the plugin on both the ephemeral main UI engine and the persistent background engine; the main UI engine attaching (e.g. just opening the app) silently hijacked the channel, so writes worked once per process then failed forever after (`FlutterJNI was detached from native C++`). Fixed by replacing the plugin's bridge entirely with same-process `IsolateNameServer` `SendPort`/`ReceivePort` pairs — a pure-Dart transport with no shared native state to hijack.
- **On Android specifically, `PRAGMA journal_mode=WAL` must go through `rawQuery()`, not `execute()`.** Android's sqflite backend rejects `execute()` for any statement that returns a result row (WAL does). Desktop unit tests (`sqflite_common_ffi`) didn't catch this — that backend tolerates `execute()` for it — so this only surfaced as a real on-device crash (`DatabaseException(unknown error (code 0 SQLITE_OK))`) during manual testing, not in CI-style test runs. Lesson: **a clean `flutter test` pass does not prove the on-device DB path works** — always do at least one real-device write/read cycle for any new sqflite usage.
- **sqflite's default `singleInstance: true` shares one native connection per file path across isolates.** The History screen (main UI engine) and the background writer both open `intents.db`; sharing a connection meant the History screen's `dispose()` closed the writer's connection too, permanently breaking writes (`DatabaseException(database_closed)`) until process restart. Fixed via `IntentStore.open(ownConnection: true)` for the History screen — its own independent connection, exactly what WAL mode was chosen to support (one writer + concurrent readers).
- **The background engine can start (at `LOCKED_BOOT_COMPLETED`) before Android's credential-encrypted storage unlocks**, so the first `IntentStore.open()` can fail (`errno 126`/`ENOKEY`) before the user's first post-reboot unlock. The original code opened the store exactly once, unawaited and uncaught — that one failure permanently broke both the cooldown check (read a null store as "no prior event," forever) and all writes (the insert listener was gated behind the same failed open). Fixed via an idempotent `_ensureIntentStore()` retried at write-time and at each triage check, so the user's next real unlock — the moment storage is guaranteed available — gets a fresh attempt.

**De-risked before building anything else:** confirmed via a throwaway instrumented spike (native source read + real-device test, including a full swipe-from-Recents cycle) that `shareData()` from the overlay isolate reliably reaches `overlayListener` subscribed in the **background** engine, surviving the main UI engine's death. This corrects the ORIGINAL plan's wording (which said "the main isolate performs the write") — the main UI engine is absent during the app's dominant "closed but monitoring" state, so the write MUST happen in the persistent background engine, which is what's built.

**Deferred, explicitly out of this sprint (enabled by it, not blocked):** the triage customization UI + an instance-based strategy (architecture ready, see `CompositePromptPolicy`); `status` (completed-vs-abandoned) on `intent_log`, since only one dismiss gesture exists; the **timer/long-session countdown** — the actual bubble+timer differentiator (§10) and the natural next big feature, notably still unshipped even by competitor Intenty.

## 5. Distribution & signing (for sharing test builds with friends)

- **v0.3.0 is signed with a real release keystore**, replacing the earlier debug-signed builds: `android/app/keystore/upload-keystore.jks`, alias `upload`. **Both the keystore and `android/key.properties` are gitignored and must never be committed** — the password is kept only in Dinesh's password manager, not in this repo or any doc. If the keystore or its password is ever lost, no future build can be signed to match it — anyone with an existing install would need a full uninstall/reinstall to get any update. `build.gradle.kts`'s release `signingConfig` falls back to debug signing automatically if `key.properties` is absent, so a fresh clone without the keystore still builds (debug-signed).
- **Sharing method:** Play listing in prep (`docs/PLAY_SUBMISSION.md`); until the closed test is live, sideload the `arm64-v8a` split APK (`flutter build apk --release --split-per-abi`; `arm64-v8a` covers essentially all phones from the last ~7+ years).
- **Known friend-onboarding snag, not an app bug:** Android 13+'s "Restricted Settings" blocks the overlay permission ("Display over other apps") on the *first* grant attempt for any sideloaded app — a deliberate OS anti-malware measure, since overlay permission + sideloading is a common phishing pattern, and it can't be worked around from inside the app. Fix, once per install: **App info → ⋮ menu → "Allow restricted settings" → confirm → then grant the permission normally.** Worth telling people this upfront rather than letting them hit the confusing "App was denied access" dialog cold.
- **Security review conclusion (2026-07-17):** no exploitable vulnerabilities found in current code — no exported components beyond the required launcher activity, the lock/unlock receiver relies on protected system broadcasts third-party apps can't spoof, zero network calls anywhere in the dependency tree, release build is non-debuggable by default, signing is now a real (non-debug) key. The one real gap found (`allowBackup` defaulting to `true`) is tracked in §2.

## 8. Engineering principles — must run well on low-end AND high-end devices

This is a hard requirement, not a nice-to-have. The app runs a persistent overlay + foreground service, which is exactly where cheap devices struggle. Every change is judged against this.

- **Overlay engine cost:** `flutter_overlay_window` spins up a *second* Flutter engine for the bubble. Keep the overlay UI minimal — no heavy widgets, images, or continuous animations in the bubble. Every MB of overlay RAM matters on a 2–3 GB device.
- **Battery / foreground-service discipline:** the bubble runs via a foreground service. Do the minimum work; avoid polling/timers that wake the CPU; coalesce UI updates. Target <2% battery/day.
- **Responsive layout:** never hardcode pixel sizes. Use logical density, `MediaQuery`, and flexible layouts so it works from small budget screens to large phones and foldables.
- **Fast unlock path:** keep the unlock → prompt path lightweight so the prompt appears within ~500ms even on slow storage. Defer non-critical init off the critical path. (Known current gap: the capture screen's cold-start of the overlay's second Flutter engine, plus the close+reopen round-trip needed when collapsing to the bubble, add real latency — pre-warming the overlay engine is a parked follow-up, not yet done.)
- **Graceful degradation:** if overlay permission is denied, or an aggressive OEM (Xiaomi/Oppo/Vivo — highly relevant for the India market) kills the service, fall back to a notification-based reminder instead of failing silently. **Not built yet** — confirmed current behavior is a silent no-op if permission is missing (see `_showCaptureScreen()` in `lib/main.dart`).
- **Test matrix:** validate on at least one low-end device (≤3 GB RAM, older Android) and one modern device. Emulators do NOT reproduce unlock events or overlay behavior — physical devices only. Always test `--release`, not just debug, when judging performance. **Still outstanding:** low-end device pass (testing so far has been on a modern device only), battery soak test vs. the <2%/day target. Landscape/rotation bubble survival has a code path (`onOrientationChanged`) — confirm on-device via `docs/TEST_PLAN.md` 57/59/60.
- **minSdk / targetSdk:** baseline is API 29 (Android 10). Going lower widens reach (meaningful for budget Android in India) but complicates the overlay stack; treat any change as a deliberate decision, not a default. Keep targetSdk current for Play compliance.

## 9. Platform & policy constraints (the fragile surface)

- The **SYSTEM_ALERT_WINDOW + AccessibilityService** permission stack is the most policy-pressured area on Android 12–16 and the single biggest existential risk to the app. Android 13+'s "Restricted Settings" gate (§5) is a concrete instance of this pressure already being felt during informal sharing, not just a theoretical Play-review risk.
- **Prefer `UsageStatsManager` over `AccessibilityService`** wherever the same signal can be obtained. Accessibility use is heavily scrutinized in Play review and can get the app pulled.
- **Onboarding is a permission cliff.** Do NOT demand overlay + accessibility on day one — that's a top drop-off risk regardless of pricing. **Whether the bubble itself is free or Pro-gated is now an open question (see §11/§12) — don't assume Pro.** The "ease into it, don't demand upfront" onboarding principle still holds either way; it's separate from the monetization decision. **Onboarding now exists** (`OnboardingScreen` via `AppLauncher`) — keep sequencing calm; don't reintroduce a cold permission ask on `HomeScreen`.
- **Smart unlock triage:** don't prompt on every unlock. Skip very short/quick unlocks to avoid friction fatigue; make cooldown and triage configurable — see §3 for the concrete Sprint 3 design.

## 10. Product strategy (keep decisions anchored here)

- **Primary competitor: Intenty** — ~2-year head start, strong press coverage, 4.8★. The unlock-prompt mechanic alone is NOT a differentiator. Our wedge is bubble + timer + session framing.
- **Behavioral caveat:** the PNAS *one sec* RCT found the deliberation prompt is the *weakest* active ingredient among friction-based interventions. Do NOT rest the product thesis on the prompt. Concentrate product energy on the bubble + timer accountability loop.
- **Repositioning:** frame as a "phone session manager," which broadens the market and reduces head-to-head overlap with Intenty.
- **Kill criteria exist** (tripwires on D1 retention, permission-grant rate, Play policy actions, Intenty shipping its own bubble, conversion, NPS). Revisit these before over-investing in any direction.
