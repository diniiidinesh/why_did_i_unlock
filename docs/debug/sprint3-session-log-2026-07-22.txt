FINDING (new, higher priority than the earlier "silent hang" flake): the overlay's
shareData() write path works exactly ONCE per app-process lifetime, then silently
stops delivering.

Evidence: every dismiss/"Just Like That" AFTER THE FIRST ONE in this log is
immediately followed by:

  W/FlutterJNI( 1097): Tried to send a platform message to Flutter, but FlutterJNI
  was detached from native C++. Could not send. Channel: x-slayer/overlay_messenger.
  Response ID: N

...and has NO matching "💾 Stored event" line. Only the very first dismiss (line 36
below, "Just Like That" at 03:02:57) actually produced a stored row.

This is NOT a triage/cooldown logic bug. It's a downstream symptom: `lastCompletedAt()`
correctly reads the DB, but the DB genuinely never receives another write after the
first one, so once >60s pass since that single stored event, the cooldown legitimately
and correctly clears on every subsequent check — it just looks like "cooldown stopped
working" because there's no new completed_at to enforce it against.

HYPOTHESIS: the overlay engine is cached and reused across showOverlay()/closeOverlay()
cycles (already documented in ARCHITECTURE.md §1/§5 — this is intentional, the engine's
Dart-side widget state survives closeOverlay()). But something about repeated
close+reopen cycles is detaching the underlying FlutterJNI native binding for that
engine's `x-slayer/overlay_messenger` channel specifically — i.e. the DART-side overlay
isolate survives, but its NATIVE-side JNI handle to send messages via BasicMessageChannel
does not survive a close+reopen. Since shareData() is (correctly, per the earlier
fire-and-forget fix) never awaited, this failure is completely silent from Dart's
perspective — no exception, no rejected Future, just a native log warning nobody sees
unless they're tailing logcat.

POSSIBLE RELATION TO THE EARLIER "SILENT HANG" FLAKE (documented separately in
BACKLOG.md): both may be manifestations of the same underlying instability in the
overlay engine's plugin-native binding after repeated show/close cycles — worth
investigating together, not necessarily as two separate bugs.

NEXT STEPS FOR WHOEVER PICKS THIS UP:
1. Reproduce: build+run, do ONE dismiss/JLK (should store fine), then do a SECOND one
   and confirm the "FlutterJNI was detached" warning appears with no stored event.
2. Check whether re-registering/re-attaching the overlay engine's plugin (or forcing a
   fresh overlay engine per cycle instead of the cached one) fixes it — this may mean
   revisiting the "cached engine is intentional" design in ARCHITECTURE.md §1, OR
   finding a way to re-establish just the messenger channel without discarding widget
   state.
3. Check flutter_overlay_window's GitHub issues for "FlutterJNI detached" / "messenger
   channel" — this smells like a known upstream plugin limitation, not necessarily
   something fixable purely in our Dart code.
4. Given this means SILENT DATA LOSS on every capture after the first one, this should
   be treated as a P0 blocker for calling Sprint 3's storage "done" — not a P2 flake.

UPDATE 3 — THE REAL "sticky, doesn't heal after opening the app" BUG: FOUND & FIXED
=================================================================================

Distinct from both earlier bugs (shareData transport = fixed via IsolateNameServer;
isActive() native hang = fixed via self-tracked _overlayIsActive). This one is a
sqflite connection-sharing bug.

SMOKING GUN (on-device 16:28, PID 13833): overlay showed + intent declared/dismissed
fine, IsolateNameServer relay delivered the message intact, but the insert failed:
  ! Ignoring malformed overlay message (DatabaseException(database_closed 1)):
    {clientId:..., kind: intent, source: custom, text: Resting, ...}
("malformed" is a misnomer — the message was valid; the DB was closed. The catch-all
in backgroundMain's port listener just labels any insert failure that way.)

ROOT CAUSE: sqflite opens databases in singleInstance mode BY DEFAULT. The History
screen (main UI engine) called IntentStore.open() on the same file the background
engine already had open → both got the SAME shared native connection. History screen's
dispose() → close() closed that shared connection → the background writer's DB is now
closed → every subsequent write throws database_closed, permanently, until process
restart. Exactly matches "broke when I opened the app, didn't heal."

FIX: IntentStore.open(ownConnection: bool). Background writer keeps the default shared
connection (singleInstance: true). History screen now opens with ownConnection: true →
singleInstance: false → its OWN independent native connection it can close on dispose
without touching the writer. Two connections to one WAL file = exactly what WAL was
chosen for (one writer + concurrent readers). This is sqflite's own documented approach
for opening a DB from multiple isolates. flutter analyze clean, all 27 tests green.
Awaiting on-device re-verification of the same app-open stress sequence.

UPDATE 4 — REBOOT BUG (case 25): IntentStore.open() failing once, permanently,
with no retry — breaks BOTH cooldown AND all future writes: FOUND & FIXED
=================================================================================

Reported symptom (owner, real device reboot 2026-07-22 17:xx): a capture prompt was
left open across a device reboot; after boot, no cooldown ever kicked in again — every
unlock either triaged on probability alone or prompted immediately, never blocked by
the 1-minute floor.

Reproduced via `flutter run --release -d A063` (a fresh engine start, same class of
event as a reboot's direct-boot service start). Log evidence, PID 4169:

  E/flutter ( 4169): Unhandled Exception: DatabaseException(open_failed
    /data/user/0/com.whydidiunlock.why_did_i_unlock/databases/intents.db)
  ...
  #7 IntentStore.open (package:why_did_i_unlock/intent_store.dart:156)
  #8 backgroundMain.<anonymous closure> (package:why_did_i_unlock/main.dart:260)

Every subsequent unlock in that same process then showed cooldown as always-clear
(`lastCompletedAt` always null) — matching the reported symptom exactly.

ROOT CAUSE: `backgroundMain()` called `_intentStore = await IntentStore.open();`
exactly ONCE, unawaited and with no try/catch, inside an IIFE that also registered the
write-relay listener only after a successful open. When that one attempt threw:
  - `_intentStore` stayed null for the rest of the process's life (no retry, ever).
  - `_showCaptureScreen`'s cooldown check read `_intentStore == null` as "no prior
    event" — a deliberate design choice for the brief window right after a NORMAL
    engine start, but never meant to survive permanently — so cooldown silently broke
    forever, not just once.
  - The write-relay `intentWritePort.listen(...)` never even ran (it was inside the
    same failed block), so every future write was ALSO silently dropped, not just
    cooldown-adjacent reads. A single bad open() call permanently disabled storage.

WHY open() failed in the first place: `backgroundMain` is the direct-boot service
entry point — it can start at LOCKED_BOOT_COMPLETED, BEFORE the user's first
post-reboot unlock, while Android's credential-encrypted storage (where
`getDatabasesPath()` resolves by default) is still locked. The very first open()
attempt raced that lock and lost. By the time the user actually unlocks (the moment
the cooldown check is needed), storage is guaranteed available again — but the old
code never tried a second time. (The `flutter run --release` repro hit the same
exception via a different trigger — most likely the databases/ directory not yet
existing on a fresh install/relaunch before any engine had created it — same code
defect, different environmental cause.)

FIX (lib/main.dart): replaced the one-shot open with `_ensureIntentStore()` — idempotent,
retries on every call rather than trusting a stale failure. Called from THREE places:
(1) best-effort unawaited at backgroundMain start (as before), (2) inside the write
listener before every insert (so a write is retried even if the listener attaches before
the store is ready), (3) at the top of _showCaptureScreen's triage block (so the exact
moment storage is guaranteed unlocked — the user's next real unlock — gets a fresh
attempt). The listener itself is now attached unconditionally and immediately (not
gated behind open() succeeding), so a same-VM backgroundMain restart can't orphan it
on a stale port either. Also added a defensive `Directory(...).create(recursive: true)`
in IntentStore.open() (lib/intent_store.dart) as a belt-and-suspenders for the
fresh-install-directory-missing trigger specifically.

flutter analyze clean, all 27 tests green. Awaiting on-device re-verification: repeat
the reboot-with-prompt-open sequence (case 25 in docs/TEST_PLAN.md) and confirm cooldown
now blocks re-prompts within 1 minute of the post-reboot unlock, and that writes still
succeed.
